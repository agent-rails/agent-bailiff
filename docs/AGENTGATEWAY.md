# agentgateway adapter

Three ExtMcp processors for agentgateway v1.7.0 (`mcpGuardrails`): decide, then custodian, both on every method's request phase (`{"*": "request"}`), and the custodian's redactor on `tools/call` responses only (`{"tools/call": "response"}`), on its own socket. All three are `failClosed`.

## Method surface

- Decide passes `initialize`, `ping` and `tools/list`, decides `tools/call`, and refuses every other hooked method with `method_refused`.
- On every hooked method the custodian removes every agent header except `accept`, `content-type`, `mcp-protocol-version`, `traceparent` and `tracestate`, plus every binding-table credential header, from the upstream request; on a release it then sets the released credential header. Decide sees only the chain headers (`requestHeaders.allowed`); the custodian has no `requestHeaders` filter, so it sees every header the agent sent, and check-config refuses a custodian `requestHeaders` entry. The gateway still adds its own `host`, `content-length`, `accept-encoding`, `mcp-method` and `mcp-name`. Pseudo-headers such as `:authority` are not forwarded as headers.
- agentgateway v1.7.0 runs no request-phase hook for `resources/subscribe`, `resources/unsubscribe`, `completion/complete` or `tasks/*`. check-config requires `mcpAuthorization.rules` to be exactly `mcp.methodName == "tools/call" || mcp.methodName == "tools/list"`; with a rule present, agentgateway denies those methods before they reach an upstream. Under that rule alone, `prompts/list` and `resources/list` return empty lists; decide refuses both before that.
- check-config requires `requestHeaderModifier` to be exactly `{"remove": [...]}` naming `authorization`, `proxy-authorization`, `cookie`, `bailiff-release` and every binding-table credential header, and naming no `x-bailiff-*` header or `traceparent`. agentgateway applies it before the processors run, on every message, and it does not remove the header the custodian sets.
- Client notifications (`notifications/initialized`, `notifications/cancelled`, `notifications/progress`, `notifications/roots/list_changed` and custom notifications) run no processor and no `mcpAuthorization` check in v1.7.0. They reach every upstream carrying every agent header except those `requestHeaderModifier` removes: the `x-bailiff-*` headers and any other header the agent adds (for example `sudo` or `x-forwarded-user`), but no agent credential header. An upstream must not trust any request header on a notification.
- check-config requires top-level `frontendPolicies` to be exactly `{"accessLog": {"remove": [...]}}` with unique field names including `mcp.error.message`. agentgateway v1.7.0 runs no response processor on a JSON-RPC error and logs its text as `mcp.error.message`, so an upstream error echoing a released credential would land in the access log. Any other access-log key (`add`, `preset`, `filter`, `otlp`, `database`) or frontend policy is refused, because it could add or ship fields check-config cannot review. `config.logging` may set only `level` and `format`; its `fields`, `filter` and `database` keys are refused for the same reason. `config.tracing` and `config.metrics` may not set `fields`, which can add `mcp.error.message` to spans or metric labels; the default span and metric attributes were not checked for error text. The removal was measured for both the text and `json` formats.
- check-config requires `statefulMode` to be `stateless`. In stateful mode the GET event stream reaches the upstream with the agent's headers and no processor. In stateless mode agentgateway answers GET and DELETE with 405.
- Not probed: client responses to server-initiated requests.

## Refusal guard

- check-config requires exactly two processors that run on responses, in list order: the redactor, then the refusal guard (`config_check.REFUSAL_GUARD`), an expression processor on `tools/call` responses. agentgateway runs response processors in list order, so the guard sees the redacted result. A processor with any method phase other than `request` or `off`, including `full`, counts as running on responses, so no other processor can rewrite an upstream answer into the refusal shape after the guard. When an upstream answer is a tool error whose only content item has `text` equal to a bailiff refusal reason, it rejects the answer, and agentgateway returns a JSON-RPC error (`-32001`) to the agent instead.
- Without it, an upstream that acted and then answered `needs_approval` or `out_of_scope` would be classified by the client as not executed, and preparing the call again would run it twice.
- agentgateway fails an expression evaluation error closed. A malformed upstream error answer therefore also becomes a JSON-RPC error.
- Gateway refusals are written by the request path and never pass through a response-phase processor, so they still reach the agent as tool errors.

## Credential echo redaction

- check-config requires one remote processor on the redactor socket (`--redactor-socket`) with methods exactly `{"tools/call": "response"}`, `failClosed`, metadata `{"clearance": "mcpGuardrails.clearance"}` and no `requestHeaders`. Decide and the custodian must be the last two request-phase processors, in that order; request-phase and response-phase processors may interleave in the list.
- The redactor reads the clearance from the metadata, takes the custodian's in-flight entry for it, and replaces each echo of the released credential in the result's strings and keys with `[redacted by agent-bailiff]`. A result without an echo passes unchanged. It also runs on tool error results. See [DECISIONS.md](DECISIONS.md) D20 for the forms it matches.
- It refuses with a `response_*` reason (`response_unmatched`, `response_unreadable`, `response_oversize`, `response_clearance_missing`, `response_internal_error`); agentgateway returns a JSON-RPC error and the client reports `OutcomeUnknown`. These reasons are disjoint from `REFUSAL_REASONS`, and the upstream has already acted. The custodian records a `refuse` entry with the reason. For `response_unreadable`, `response_oversize` and a `response_internal_error` after the release is found, the entry carries the release's handles and the release entry as `parent_entry`. For `response_unmatched` it decodes the clearance without checking its expiry and, when the signature verifies against the pinned decide keys and the clearance names this custodian and its decider, records the entry with the clearance's handles and decide's entry as `parent_entry`, once per operation while that operation is among its last 65,536 recorded refusals. A missing clearance, one that does not verify, an internal error before the release is found, and an append the docket does not take are logged, not recorded. These entries carry no `latency_ms`. The append runs on the redactor worker before the refusal returns, behind the same docket client lock as releases, so a slow docket sink slows refused results and the releases that share the client; the `credential_echo` alert already did the same.
- check-config requires `mcp.policies.timeout` with `requestTimeout` and `backendRequestTimeout`, each an integer with `ms`, `s` or `m` and at most 120 s; an optional `responseIdleTimeout` has the same cap. The custodian owns the 120 s cap and requires `inflight_ttl` (default 180 s) of at least the cap plus 30 s, so an in-flight entry outlives the slowest non-streamed call. A timed-out call never reaches the redactor, and its in-flight entry expires after `inflight_ttl`. Against the pinned v1.7.0 binary, neither `requestTimeout` nor `backendRequestTimeout` bounds an event-stream body once the upstream has sent its headers. `responseIdleTimeout` cuts a stream that stays silent longer than the timeout, and the client reads a truncated body after the upstream acted; it does not cut a stream that keeps sending messages, such as progress notifications. So a stream held open past `inflight_ttl` can act upstream and then end in a JSON-RPC error `response_unmatched` (-32001); the custodian records the refusal under decide's entry and the client reports `OutcomeUnknown`. `tests/test_agentgateway_e2e.py` pins the timeout behaviour, the `response_unmatched` error and the docket contents with 1 s timeouts; the client's `OutcomeUnknown` mapping is pinned in `tests/test_client.py`.
- agentgateway v1.7.0 sends no JSON-RPC error and no event-stream message other than the result through a response processor, so the redactor cannot see an echo there. A client that reaches the gateway directly, the agent's uid included, can read them.
- A raw result over 4 MiB (`MAX_RESULT_BYTES`) is refused as `response_unreadable`. `response_oversize` applies only to a result with an echo whose redacted re-encoding exceeds 4 MiB: it is re-encoded with ASCII escapes, so a result near the cap with many non-ASCII characters can pass the raw check and fail after redaction.
- The redactor's gRPC server keeps grpcio's default 4 MiB receive limit for the whole `McpResponse`, so a result within about 1 KiB of the 4 MiB cap is refused with `RESOURCE_EXHAUSTED` ("Received message larger than max") before the redactor runs. A raw result over the cap therefore never reaches the redactor's own size check. Observed on 2026-11-26 with grpcio 1.85.3: a 4,193,280-byte result with a 600-character clearance passed; 4,194,204 bytes was refused.
- agentgateway v1.7.0, in the tested config, refuses an upstream `tools/call` response body over about 2 MiB (2,097,114 bytes passed, 2,098,138 failed) with HTTP 500 and JSON-RPC `-32603` "failed to send message", and logs "body exceeded buffer limit". This happens after the upstream acted and before any response processor runs; the client reports `OutcomeUnknown("http_500")`. Whether the limit is configurable was not checked.
- A redactor shed reaches the agent as HTTP 200 with JSON-RPC `-32603` "guardrail check failed", the same answer as an unreachable processor; agentgateway drops the gRPC status. A `response_*` refusal reaches it as `-32001` with the reason as the message. The client reports both as `OutcomeUnknown` and never resends the call (`tests/test_client.py`).
- Nothing above the client may retry an `OutcomeUnknown` automatically without first reconciling the target's state. A fresh prepare carries a fresh nonce, which changes the request digest and the op_id, so the custodian's once-only claim does not stop it and a non-idempotent tool can run twice.
- Capacity was measured on 2026-11-27 on one host shared with other work (Apple M1 Max, 10 cores, macOS 26.6, Python 3.13.15, grpcio 1.85.3, agentgateway v1.7.0, load average 8 to 20 at the start of each run), so the numbers are noisy. The benches are opt-in (`AGENT_BAILIFF_TEST_REDACTOR_BENCH=1`) and write `benchmarks/*.local.json`, which is not committed; the 2026-11-26 files in `benchmarks/` are an earlier direct run. p50 and p99 count successful calls only.
- Direct to the redactor socket (`tests/test_redactor_load_bench.py`, a gRPC client without agentgateway): with one worker and one client, text took 0.9 ms (64 KiB), 15 ms (2 MiB) and 34 ms (4 MiB) p50 without an echo and 3.1, 38 and 62 ms with one; about 110-byte JSON objects took 5.8, 165 and 330 ms without an echo and 7.8, 189 and 394 ms with one. Throughput from 4 to 128 clients was 0.76-1.63x the one-client rate (median 1.01) with one worker, and two workers ran at 0.67-1.43x the one-worker rate per setting (median 1.03), consistent with the scan holding the GIL. Of 512, 1,024, 2,048 and 4,096 calls at 16, 32, 64 and 128 clients, one worker shed 0, 42, 243 and 634 and two workers 0, 46, 174 and 740; the 10 s deadline (`DEADLINE_EXCEEDED`) took 5, 39, 210 and 727 with one worker and 2, 45, 228 and 657 with two. At 16 clients or fewer the only failures were deadlines on 4 MiB of objects with an echo. 2 MiB of objects reached 3.6-5.1 s p99 at 16 clients. Another thread in the process woke up to 46 ms late (p99), against 2.6 and 7.4 ms idle. The process's peak resident set grew from 88 MiB to 756 MiB over the one-worker grid and to 927 MiB after the two-worker grid in the same process.
- Through agentgateway (`tests/test_redactor_gateway_load_bench.py`): `BailiffClient` threads called a non-idempotent `create_ticket` upstream that counts executions per ticket, through decide, the custodian and the redactor, at 1 to 64 clients, with results of 64 KiB, 1 MiB, just under 2 MiB and just under 4 MiB, each with and without an echo. With one worker and with two, no call ran twice upstream, none was refused after the upstream acted, and every `OutcomeUnknown` came after the upstream acted. At 16 clients or fewer no call ended in `-32603` except 2 MiB of objects with an echo (6 of 32 calls with one worker, 2 of 32 with two). At 64 clients 30-83% of calls ended as `OutcomeUnknown("jsonrpc_error_-32603")` in every setting up to 2 MiB except 64 KiB without an echo, which shed none. Every 4 MiB result ended as `OutcomeUnknown("http_500")` at every concurrency, from the gateway body limit above. With one worker and one client, throughput was 97 calls a second for 64 KiB of text, 7.3 for 1 MiB of objects and 1.9 for 2 MiB, and 2 MiB of objects reached 11-14 s p99 at 32 and 64 clients. The custodian's `check_request` time per `tools/call` was 3-9 ms p50 at one client and rose with result size under load, to 191 ms p50 and 1.66 s p99 with 2 MiB of objects at 64 clients and one worker (0.72 s p99 with two), consistent with the scan holding the GIL in the process the request processor shares. After each setting the custodian held one in-flight entry for each `OutcomeUnknown` whose result the redactor never took, a shed or an `http_500`, until `inflight_ttl`. agentgateway's resident set, read after each setting drained, reached 1,519 MiB.
- The in-flight map (`tests/test_inflight_load_bench.py`, in one process): reserve and take took 2-3.5 µs p50 from 1 to 64 threads, over an empty map and one holding 2,048 entries. p99 stayed under 11 µs up to 16 threads and was about 9 ms at 64 threads, with a 73 ms maximum, from lock and GIL waits. A reserve that swept 4,096 entries expired at once took 3.1 ms. With the defaults, 8 tenants at 512 entries each fill the map and the next tenant is refused with "in-flight release map is full"; the 8 MiB byte bound holds 4,096 entries with header values up to 2 KiB, 2,048 at 4 KiB and 512 at 16 KiB.
- The defaults stay. `response_workers` stays 1, since two workers gave no consistent gain in either bench. Admission stays at 16: below it nothing was shed except the slowest results, and a lower limit would shed fast results that pass today. No separate overloaded signal: agentgateway v1.7.0 drops the gRPC status, so any shed reaches the agent as the same `-32603`, and the custodian's shed warnings are the operator's signal. The client reports every shed, timeout and `http_500` as `OutcomeUnknown` and sends the call once (`tests/test_client.py`, `tests/test_proxy.py`).
- At 10x load the single scan saturates first: about 2-10 results a second for 1-2 MiB of objects on this host, so most calls shed or time out after the upstream acted. Each such call holds its in-flight entry for `inflight_ttl`: at 180 s, 2.8 unknown outcomes a second fill one tenant's 512 entries and 22.8 a second fill the map, after which releases are refused before the upstream acts (`release_refused`). Gateway memory grows with buffered results. Fixes, not built: a scanner that does not hold the request processor's GIL, per-tenant admission, freeing the in-flight entry for a call the redactor sheds, and a smaller gateway body limit.
- Non-goal: per-tenant redactor admission. The 16-call admission limit is shared by all tenants, so one tenant with large results can fill it and shed other tenants' responses after their upstreams acted. Per-tenant admission is not built.
- `inflight_per_tenant` (default 512) caps one tenant's share of `inflight_max` (default 4096); keep it well below `inflight_max` so a few tenants cannot fill the map.

## Clearance visibility

- Decide returns the signed clearance in the `metadata` bag of its `CheckRequest` result. agentgateway records that bag in its access log and exposes it to backend CEL as `mcpGuardrails.clearance`.
- The clearance carries no secret. A copied clearance does not release a credential on its own: the custodian re-verifies the chain, leaf proof and request digest from the call itself, checks the ledger reservation, and claims the op_id once.

## Processor sockets

- Each processor listens on a unix socket in a 0750 directory with the gateway's group, socket mode 0660.
- The processor accepts each connection itself, refuses any peer whose uid is not the configured gateway uid, and relays accepted connections to its gRPC server on a socket in a 0700 directory.
- The relay holds at most 64 connections and has no idle timeout. A connection over the cap is closed.
- A refused, closed or unreachable processor fails the call closed, because check-config requires `failClosed`.
- The decide and custodian request gRPC servers each run 8 workers and admit at most 256 concurrent calls; a call past that is refused with `RESOURCE_EXHAUSTED`, which fails it closed. The limit is fixed. At the quickstart's measured rate (about 115 calls a second at 32 clients), 256 queued calls drain well inside the gateway's 10-second processor timeout.
- The redactor's gRPC server scans `response_workers` results at a time (default 1, at most 2) and admits at most 16 concurrent calls, so a large result never takes a release's gRPC worker; releases still slow under large results, as measured above. The limit is applied in the handler: a call past it is refused with `RESOURCE_EXHAUSTED` after the upstream acted. The custodian logs the first shed, then at most one warning every 10 seconds with the number shed since the last warning and since start; sheds after the last warning are counted in the next one. A call that gives up while waiting for a scan slot frees its admission slot within 0.1 seconds and is not scanned. gRPC itself refuses a call with `RESOURCE_EXHAUSTED` and no log line when 32 calls are already in its handlers, counting calls being refused. Under sustained overload that is common: in a local probe with 200 clients about half of all sheds were refused by gRPC, so the logged total undercounts sheds.
- agentgateway abandons a processor call after 10 seconds. grpcio drops a call the gateway abandoned while it was still queued, so the processor never sees it and it never reserves a ledger slot or claims an op_id. A call already inside the processor runs to completion; its result is discarded and its op_id stays claimed.

## check-config

- `python -m agent_bailiff.adapters.agentgateway check-config` validates a JSON gateway config at startup only.
- agentgateway watches its config file and reloads it on change, so a later edit is not checked. The config file must be writable only by its owner, and that owner must be neither the gateway's user nor an agent's user.
- The mcp target `host` of a gateway-bound service must be `https`, or `http` only to `127.0.0.1` or `[::1]`. A host without a scheme, alone or with `port` and `path`, is `http`, as agentgateway v1.7.0 treats it. A host with a non-ASCII character, user info, a query, a fragment, whitespace, a control character, a backslash, or an empty, zero or out-of-range port is refused. In the split form, `port` must be an integer from 1 to 65535 and `path` must start with a single `/` and hold only RFC 3986 path characters, because agentgateway v1.7.0 builds the request URI by appending `path` to `host:port`. A host without a scheme must be `host` or `host:port`, with `[::1]` bracketed. In the split form, with `port` or `path`, `host` must not carry a scheme: agentgateway v1.7.0 treats a split-form host as an authority with TLS off and rejects a scheme, so only the `https://` URI form gives TLS to a remote upstream. A service name such as `gitea-mcp` is refused over `http`: an absent single-label name falls through to the host resolver, for example while its container restarts, so the name does not fix the peer; the kernel fixes a loopback peer. `localhost` is refused over `http` too, since agentgateway resolves it after the check. Use `https://` for every other host, with `backendTLS.root` for a private CA (D24).
- Top-level `gateways` may hold only `default`, which holds only `port`, from 1 to 65535, and `tls`, which holds only `cert` and `key`, each a non-empty path. `mcp.port` must then be absent, so no plaintext listener stays beside the TLS one. Against the pinned v1.7.0 binary, `tests/test_agentgateway_e2e.py` runs the refusal, the release through both processors and echo redaction through that listener.
- A target's `backendTLS` may hold only a non-empty string `root`. `insecure`, `insecureHost`, `hostname` and every other key are refused.
- `--stack-host HOST`, repeatable, names a host a private CA serves. An `https` target to it without `backendTLS.root` is refused, since the system roots let any public CA vouch for that name. The quickstart passes `stub-upstream` and `gitea-mcp-tls`. check-config refuses to run with neither `--stack-host` nor `--no-stack-hosts`, so a deployment cannot skip the check by leaving the flag out; `--no-stack-hosts` states that no target host is served by a private CA, and is refused beside `--stack-host`.

## tools/call params

- Params may hold only `name`, `arguments` and `_meta`. Any other key is refused as `malformed_request`.
- `_meta` may hold only `progressToken` (string or integer), `io.modelcontextprotocol/protocolVersion` (string), `io.modelcontextprotocol/clientInfo` (object) and `io.modelcontextprotocol/clientCapabilities` (object). Any other key or type is refused as `malformed_request`.
- These `_meta` values are not part of the request digest, the leaf proof or the clearance; they reach the upstream unbound. Binding them needs a change to the agent-side proof.

## Proof headers on notifications

- Client notifications fan out to every upstream and carry the agent's `x-bailiff-*` headers, including the leaf proof for whatever request the agent is about to make.
- A leaf proof binds one request: tool id, resource, arguments and nonce. Its op_id is claimed once, and the route table maps each tool id and resource to one upstream. The worst case is therefore an upstream that submits the operation first: it runs once, at the upstream routed for it, with the agent's arguments, and the agent's own call is refused (`already_issued` from decide). The credential is not released to the upstream that replayed the proof. This reasoning has not been executed as a test.
- Agent clients should send the `x-bailiff-*` headers only on `tools/call`.

## Batches

- agentgateway v1.7.0 rejects a JSON-RPC batch with HTTP 400 ("fail to deserialize request body: unrecognized JSON-RPC message") before any processor or upstream call.
