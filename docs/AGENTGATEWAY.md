# agentgateway adapter

Three ExtMcp processors for agentgateway v1.7.0 (`mcpGuardrails`): decide, then custodian, both on every method's request phase (`{"*": "request"}`), and the custodian's redactor on `tools/call` responses only (`{"tools/call": "response"}`), on its own socket. All three are `failClosed`.

## Method surface

- Decide passes `initialize`, `ping` and `tools/list`, decides `tools/call`, and refuses every other hooked method with `method_refused`.
- On every hooked method the custodian removes every agent header except `accept`, `content-type`, `mcp-protocol-version`, `traceparent` and `tracestate`, plus every binding-table credential header, from the upstream request; on a release it then sets the released credential header. Decide sees only the chain headers (`requestHeaders.allowed`); the custodian has no `requestHeaders` filter, so it sees every header the agent sent, and check-config refuses a custodian `requestHeaders` entry. The gateway still adds its own `host`, `content-length`, `accept-encoding`, `mcp-method` and `mcp-name`. Pseudo-headers such as `:authority` are not forwarded as headers.
- agentgateway v1.7.0 runs no request-phase hook for `resources/subscribe`, `resources/unsubscribe`, `completion/complete` or `tasks/*`. check-config requires `mcpAuthorization.rules` to be exactly `mcp.methodName == "tools/call" || mcp.methodName == "tools/list"`; with a rule present, agentgateway denies those methods before they reach an upstream. Under that rule alone, `prompts/list` and `resources/list` return empty lists; decide refuses both before that.
- check-config requires `requestHeaderModifier` to be exactly `{"remove": [...]}` naming `authorization`, `proxy-authorization`, `cookie`, `bailiff-release` and every binding-table credential header, and naming no `x-bailiff-*` header or `traceparent`. agentgateway applies it before the processors run, on every message, and it does not remove the header the custodian sets.
- Client notifications (`notifications/initialized`, `notifications/cancelled`, `notifications/progress`, `notifications/roots/list_changed` and custom notifications) run no processor and no `mcpAuthorization` check in v1.7.0. They reach every upstream carrying every agent header except those `requestHeaderModifier` removes: the `x-bailiff-*` headers and any other header the agent adds (for example `sudo` or `x-forwarded-user`), but no agent credential header. An upstream must not trust any request header on a notification.
- check-config requires `statefulMode` to be `stateless`. In stateful mode the GET event stream reaches the upstream with the agent's headers and no processor. In stateless mode agentgateway answers GET and DELETE with 405.
- Not probed: client responses to server-initiated requests.

## Refusal guard

- check-config requires exactly two processors that run on responses, in list order: the redactor, then the refusal guard (`config_check.REFUSAL_GUARD`), an expression processor on `tools/call` responses. agentgateway runs response processors in list order, so the guard sees the redacted result. A processor with any method phase other than `request` or `off`, including `full`, counts as running on responses, so no other processor can rewrite an upstream answer into the refusal shape after the guard. When an upstream answer is a tool error whose only content item has `text` equal to a bailiff refusal reason, it rejects the answer, and agentgateway returns a JSON-RPC error (`-32001`) to the agent instead.
- Without it, an upstream that acted and then answered `needs_approval` or `out_of_scope` would be classified by the client as not executed, and preparing the call again would run it twice.
- agentgateway fails an expression evaluation error closed. A malformed upstream error answer therefore also becomes a JSON-RPC error.
- Gateway refusals are written by the request path and never pass through a response-phase processor, so they still reach the agent as tool errors.

## Credential echo redaction

- check-config requires one remote processor on the redactor socket (`--redactor-socket`) with methods exactly `{"tools/call": "response"}`, `failClosed`, metadata `{"clearance": "mcpGuardrails.clearance"}` and no `requestHeaders`. Decide and the custodian must be the last two request-phase processors, in that order; request-phase and response-phase processors may interleave in the list.
- The redactor reads the clearance from the metadata, takes the custodian's in-flight entry for it, and replaces each echo of the released credential in the result's strings and keys with `[redacted by agent-bailiff]`. A result without an echo passes unchanged. It also runs on tool error results. See [DECISIONS.md](DECISIONS.md) D20 for the forms it matches.
- It refuses with a `response_*` reason (`response_unmatched`, `response_unreadable`, `response_oversize`, `response_clearance_missing`, `response_internal_error`); agentgateway returns a JSON-RPC error and the client reports `OutcomeUnknown`. These reasons are disjoint from `REFUSAL_REASONS`, and the upstream has already acted.
- check-config requires `mcp.policies.timeout` with `requestTimeout` and `backendRequestTimeout`, each an integer with `ms`, `s` or `m` and at most 120 s; an optional `responseIdleTimeout` has the same cap. The custodian owns the 120 s cap and requires `inflight_ttl` (default 180 s) of at least the cap plus 30 s, so an in-flight entry outlives the slowest non-streamed call. A timed-out call never reaches the redactor, and its in-flight entry expires after `inflight_ttl`. Against the pinned v1.7.0 binary, neither `requestTimeout` nor `backendRequestTimeout` bounds an event-stream body once the upstream has sent its headers. `responseIdleTimeout` cuts a stream that stays silent longer than the timeout, and the client reads a truncated body after the upstream acted; it does not cut a stream that keeps sending messages, such as progress notifications. So a stream held open past `inflight_ttl` can act upstream and then end in a JSON-RPC error `response_unmatched` (-32001), with no docket record of the refusal; the client reports `OutcomeUnknown`. `tests/test_agentgateway_e2e.py` pins the timeout behaviour, the `response_unmatched` error and the docket contents with 1 s timeouts; the client's `OutcomeUnknown` mapping is pinned in `tests/test_client.py`.
- agentgateway v1.7.0 sends no JSON-RPC error and no event-stream message other than the result through a response processor, so the redactor cannot see an echo there. A client that reaches the gateway directly, the agent's uid included, can read them.
- A raw result over 4 MiB (`MAX_RESULT_BYTES`) is refused as `response_unreadable`. `response_oversize` applies only to a result with an echo whose redacted re-encoding exceeds 4 MiB: it is re-encoded with ASCII escapes, so a result near the cap with many non-ASCII characters can pass the raw check and fail after redaction.
- The redactor's gRPC server keeps grpcio's default 4 MiB receive limit for the whole `McpResponse`, so a result within about 1 KiB of the 4 MiB cap is refused with `RESOURCE_EXHAUSTED` ("Received message larger than max") before the redactor runs. A raw result over the cap therefore never reaches the redactor's own size check. Observed on 2026-11-26 with grpcio 1.85.3: a 4,193,280-byte result with a 600-character clearance passed; 4,194,204 bytes was refused.
- agentgateway v1.7.0, in the tested config, refuses an upstream `tools/call` response body over about 2 MiB (2,097,114 bytes passed, 2,098,138 failed) with HTTP 500 and JSON-RPC `-32603` "failed to send message", and logs "body exceeded buffer limit". This happens after the upstream acted and before any response processor runs; the client reports `OutcomeUnknown("http_500")`. Whether the limit is configurable was not checked.
- A redactor shed reaches the agent as HTTP 200 with JSON-RPC `-32603` "guardrail check failed", the same answer as an unreachable processor; agentgateway drops the gRPC status. A `response_*` refusal reaches it as `-32001` with the reason as the message. The client reports both as `OutcomeUnknown` and never resends the call (`tests/test_client.py`).
- Nothing above the client may retry an `OutcomeUnknown` automatically without first reconciling the target's state. A fresh prepare carries a fresh nonce, which changes the request digest and the op_id, so the custodian's once-only claim does not stop it and a non-idempotent tool can run twice.
- Measured on one host (`benchmarks/redactor-load-1-worker-2026-11-26.json` and `-2-worker-`, Apple M1 Max, 10 cores, macOS 26.6, Python 3.13.15, grpcio 1.85.3, load average 7 to 12 from other work): a gRPC client called the redactor socket directly, without agentgateway. p50 and p99 count successful calls only. With one worker and one client, a text result took 0.9 ms (64 KiB), 16 ms (2 MiB) and 32 ms (4 MiB) p50 without an echo, and about 1.8-2.9x that with one; a result of about 110-byte JSON objects took 5 ms, 163 ms and 329 ms. Throughput with 4 to 64 clients was 0.94-1.30x the one-client rate with one worker and 1.00-1.35x with two. Nothing was shed up to 16 clients. For results of 1 MiB and up, 34-50% of calls were shed at 32 clients and 69-75% at 64. At 16 clients, 2 MiB of objects reached 5.5 s p99. Only 4 MiB of objects hit the 10 s deadline (`DEADLINE_EXCEEDED`), counted as one worker and two workers: with an echo, 2 and 1 of 32 calls at 16 clients, 19 and 11 of 64 at 32 clients, and 7 and 3 of 128 at 64 clients; without an echo, 2 and 1 of 64 at 32 clients. Two-worker throughput was 0.73-1.43x the one-worker rate per setting with no consistent gain, consistent with the scan holding the GIL. Another thread in the process woke up to about 40 ms late (p99) under the largest results, against 3.9 and 5.3 ms p99 idle. Not measured: through agentgateway, other hosts, or concurrent releases on the request processor.
- Non-goal: per-tenant redactor admission. The 16-call admission limit is shared by all tenants, so one tenant with large results can fill it and shed other tenants' responses after their upstreams acted. Per-tenant admission is tracked on #92.
- `inflight_per_tenant` (default 512) caps one tenant's share of `inflight_max` (default 4096); keep it well below `inflight_max` so a few tenants cannot fill the map.

## Clearance visibility

- Decide returns the signed clearance in the `metadata` bag of its `CheckRequest` result. agentgateway records that bag in its access log and exposes it to backend CEL as `mcpGuardrails.clearance`.
- The clearance carries no secret. A copied clearance does not release a credential on its own: the custodian re-verifies the chain, leaf proof and request digest from the call itself, checks the ledger reservation, and claims the op_id once.

## Processor sockets

- Each processor listens on a unix socket in a 0750 directory with the gateway's group, socket mode 0660.
- The processor accepts each connection itself, refuses any peer whose uid is not the configured gateway uid, and relays accepted connections to its gRPC server on a socket in a 0700 directory.
- The relay holds at most 64 connections and has no idle timeout. A connection over the cap is closed.
- A refused, closed or unreachable processor fails the call closed, because check-config requires `failClosed`.
- Each gRPC server runs 8 workers and admits at most 256 concurrent calls; a call past that is refused with `RESOURCE_EXHAUSTED`, which fails it closed. The limit is fixed. At the quickstart's measured rate (about 115 calls a second at 32 clients), 256 queued calls drain well inside the gateway's 10-second processor timeout.
- The redactor's gRPC server runs `response_workers` workers (default 1, at most 2) and admits at most 16 concurrent calls, so releases never wait behind a large result. A call past that is refused with `RESOURCE_EXHAUSTED` after the upstream acted.
- agentgateway abandons a processor call after 10 seconds. grpcio drops a call the gateway abandoned while it was still queued, so the processor never sees it and it never reserves a ledger slot or claims an op_id. A call already inside the processor runs to completion; its result is discarded and its op_id stays claimed.

## check-config

- `python -m agent_bailiff.adapters.agentgateway check-config` validates a JSON gateway config at startup only.
- agentgateway watches its config file and reloads it on change, so a later edit is not checked. The config file must be writable only by its owner, and that owner must be neither the gateway's user nor an agent's user.
- The mcp target `host` of a gateway-bound service must be `https`, or `http` only to `127.0.0.1`, `localhost`, `[::1]` or a single-label service name. A host without a scheme, alone or with `port` and `path`, is `http`, as agentgateway v1.7.0 treats it. A host with a non-ASCII character, user info, a query, a fragment, whitespace, a control character, a backslash, or an empty, zero or out-of-range port is refused. In the split form, `port` must be an integer from 1 to 65535 and `path` must start with a single `/` and hold only RFC 3986 path characters, because agentgateway v1.7.0 builds the request URI by appending `path` to `host:port`. A host without a scheme must be `host` or `host:port`, with `[::1]` bracketed. In the split form, with `port` or `path`, `host` must not carry a scheme: agentgateway v1.7.0 treats a split-form host as an authority with TLS off and rejects a scheme, so only the `https://` URI form gives TLS to a remote upstream. The supported deployment is single host: gateway, bailiff and upstreams on one Docker host or machine. A plain-http single-label name is trusted to resolve inside that host's container network, so DNS on that network is in the trusted computing base. The check validates name syntax, not where a name resolves. Any hop that leaves the host must use `https://`; the check refuses dotted names and IP literals over `http`. Channel authentication (TLS on every non-loopback hop) is required before multi-host support and is tracked in #86.
- A target's `backendTLS` may hold only a non-empty string `root`. `insecure`, `insecureHost`, `hostname` and every other key are refused.

## tools/call params

- Params may hold only `name`, `arguments` and `_meta`. Any other key is refused as `malformed_request`.
- `_meta` may hold only `progressToken` (string or integer), `io.modelcontextprotocol/protocolVersion` (string), `io.modelcontextprotocol/clientInfo` (object) and `io.modelcontextprotocol/clientCapabilities` (object). Any other key or type is refused as `malformed_request`.
- These `_meta` values are not part of the request digest, the leaf proof or the clearance; they reach the upstream unbound. Binding them needs a change to the agent-side proof.

## Proof headers on notifications

- Client notifications fan out to every upstream and carry the agent's `x-bailiff-*` headers, including the leaf proof for whatever request the agent is about to make.
- A leaf proof binds one request: tool id, resource, arguments and nonce. Its op_id is claimed once, and the route table maps each tool id and resource to one upstream. The worst case is therefore an upstream that submits the operation first: it runs once, at the upstream routed for it, with the agent's arguments, and the agent's own call is refused (`already_issued` from decide). The credential is not released to the upstream that replayed the proof. This reasoning has not been executed as a test.
- Agent clients should send the `x-bailiff-*` headers only on `tools/call`.

## Batches

- agentgateway v1.7.0 rejects a JSON-RPC batch with HTTP 400 ("fail to deserialize request body: unrecognized JSON-RPC message") before any processor or upstream call.
