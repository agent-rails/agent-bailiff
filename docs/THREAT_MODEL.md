# Threat model

Scope: agent-bailiff with the agentgateway v1.7.0 adapter, each component under its own OS user on one host, as described in [ARCHITECTURE.md](ARCHITECTURE.md). On managed clusters (GKE, EKS) the effector serves reads only; see [MANAGED_CLUSTERS.md](MANAGED_CLUSTERS.md).

## Assets

- Credentials in the custodian's store, and the key encryption key.
- Each component's signing key.
- The ledger: reservations, revocations and issued state.
- The suspension switch.
- The docket: the record of decisions, releases, control actions and issued task roots (grants).
- The effector's cluster token and audit token, and the custodian's release key.
- The power to mint the effector's and audit account's tokens, held by the off-host minter and by every principal with `create` on their `serviceaccounts/token`.

## Attackers

1. **A hijacked agent**, for example through prompt injection. It holds a valid task root, links and agent key, and can send any MCP traffic the gateway accepts.
2. **A compromised decide.** It holds decide's key and the ledger writer, but no credentials.
3. **A compromised upstream MCP server.** It receives every request routed to it, including the credential header. For catalog tools the upstream is the effector, which agent-bailiff owns.
   - 3b. **A compromised effector.** It holds the effector's cluster token and audit token, but no credential store and no signing key the custodian or decide trusts.
4. **A local user** who is not root and is not one of the component users, including a member of the ledger group who is not decide.
5. **An operator error**, such as a misconfigured gateway, a permissive directory mode or a wrong config path.

Root on the host is trusted. It can read every key and every file.

## Trust boundaries

- Agent to gateway: the MCP connection. The agent is untrusted.
- Gateway to processors: Unix sockets in a 0750 directory with the gateway's group. Each processor checks the peer uid on accept.
- Decide to custodian: the clearance, signed by decide and verified with the custodian's pinned decide keys. It is necessary but not sufficient. The gateway carries it as processor metadata. Against v1.7.0, agent headers named after it, `params.clearance` and a top-level `mcpGuardrails.clearance` neither override the clearance decide issued nor supply one when decide sets none; decide refuses a `params._meta.clearance` as `malformed_request` before the custodian runs.
- Components to docket: a Unix socket; the sink checks the peer uid and each writer's pinned key, sequence, previous hash and record type. The issuer writes grants only.
- Decide to custodian through the ledger and suspension directory: decide and control, both as decide's uid, write; the custodian reads through the ledger group.
- Custodian to effector: the release, signed by the custodian and verified with the effector's pinned keys, carried by the gateway over 127.0.0.1.
- Effector to Kubernetes: HTTPS with a pinned CA; the cluster enforces the generated RBAC and admission policies. See [EFFECTOR.md](EFFECTOR.md).

## Threats and mitigations

| Threat | Mitigation |
|---|---|
| A hijacked agent calls a tool or resource outside its task | Decide verifies the chain and leaf proof, and refuses out-of-scope calls and unknown costs. The custodian re-verifies the same proof itself. |
| A task meant to read one resource and write another can also write the first, because its scope lists both tools and both resources | A scope is a list of permissions, and a call is allowed only when one permission covers both its tool and its resource, with its cost at most that permission's `max_cost_per_call` (D21). Decide and the custodian run the same check on the leaf scope (`out_of_scope`, `cost_over_call_cap`). A delegated link narrows per permission: a child permission that takes tools or resources from two parent permissions is refused at `delegate` and at verification. |
| A grant ending mid-segment, such as `gitea/repos/acme-*` or `gitea.issues_*`, covers a resource or tool the issuer did not mean (`acme-evil`, `gitea.issues_delete`) | Decide and the custodian each refuse a call whose root or any link scope, not only the leaf, holds a resource pattern that is not exact or ending at `/*`, or a tool pattern that is not exact or ending at `.*` (`unbounded_scope`). `task issue` refuses either at issue, and the custodian refuses to load a binding with such a resource or any tool pattern. Templated routes fill each placeholder, which must be a whole segment, from an identifier argument (route documents) or a DNS-label argument (catalogs), so an argument cannot add a segment, `..` or text to another segment. |
| A hijacked agent replays a call | The leaf proof binds tool, resource, arguments and nonce. The op_id is reserved in decide's ledger, and claimed once in the custodian's claims database. |
| A hijacked agent sends its own credential headers, identity headers such as `sudo` or `x-forwarded-user`, or tampers with `x-bailiff-*` headers | On every hooked method the custodian removes every agent header except `accept`, `content-type`, `mcp-protocol-version`, `traceparent` and `tracestate`, and every bound credential header, from the upstream request. check-config requires a gateway header modifier that removes `authorization`, `proxy-authorization`, `cookie`, `bailiff-release` and every bound credential header, and refuses one that removes any `x-bailiff-` header or `traceparent`. |
| A compromised decide asks the custodian for any credential | The custodian takes the binding from its own table, re-verifies the chain, leaf proof and request digest from the call, checks the reservation, claims each op_id once, and rate-limits per task. It releases only credentials covered by authority the caller can present. |
| A copied clearance is reused | It is bound to one op_id, audience, request digest and expiry, and the op_id can be claimed once. A clearance in the gateway access log releases nothing on its own. |
| Bulk decryption of the credential store | Data keys are wrapped per credential, with tenant, credential id and target as associated data. Decryption happens only in the custodian, after verification. |
| An operator revokes a task root, link, task or tenant, or suspends every call, and a call still goes through | Control revokes through the ledger, which decide and the custodian both read. Suspension is checked by decide before it issues a clearance, and by the custodian just before it claims a release. |
| Suspension state is swapped or faked | The suspension directory's parent must be owned by root or decide, be in the ledger group, and not be group or other writable. The directory is opened relative to that parent without following symlinks. Anything unverifiable counts as suspended. |
| A forged or altered docket record | Records are signed with pinned keys and chained per writer. The sink refuses a bad signature, unknown key id, wrong sequence or broken chain. |
| A pinned writer key signs records claiming another component's hop, to change a task's principal, counts or revoke record in `docket tasks`, or a root's use in `docket grants` | `docket grants` counts allows only from `--decide-pin` writers. `docket tasks` counts a `decide`, `custodian` or `control` record only from a writer pinned for that hop (`--decide-pin`, `--custodian-pin`, `--control-pin`), reports the others on stderr and exits 3. PRINCIPAL and `record` come only from decide records; a grant never sets the principal. |
| A grant writer lists a task as `granted` in a tenant its issuer does not serve, or hands out a `record` for it | `docket tasks --issuers` checks every grant's root against the issuer allowance, as control does. A root that fails sets neither `granted`, `expires_at`, `record` nor `roots`, so a revocation naming only its binding does not mark the task; its time is replaced by the first trusted record's. The row is `invalid` only when no grant of the task passes, and the command exits 4. Only `verified` rows are selected for revoke in the documented pipeline. |
| A forged or tampered record is used for control | Control verifies the signature and pinned key id, and refuses its own writer's records. It also refuses a record whose tenant handle does not match its tenant. |
| A grant writer revokes a task of another tenant, or a writer appends a record type it does not own | Each writer appends one record type: writers in `grant_writers` (or pinned with `--grant-pin`) only grants, every other writer only entries; the sink refuses, and readers reject, the other type as `wrong_record_type`. Control revokes from a grant only when the root in it verifies against an issuer key in control's `issuers` and that issuer's allowance covers the root's tenant, principal, budget and depth. |
| An upstream acts, then answers with a bailiff refusal reason so the agent prepares the call again | check-config requires a response-phase refusal guard on `tools/call` that turns an upstream tool error whose only content is a refusal reason into a JSON-RPC error; the client classifies it as `OutcomeUnknown`. Gateway refusals never pass a response-phase processor. |
| An upstream returns the released credential in its `tools/call` result, raw or encoded, so it reaches the agent | The custodian keeps the released value for that call and its redactor, which check-config requires before the refusal guard, replaces each echo in the result's strings with a marker and writes a `credential_echo` alert linked to the release. A result the redactor cannot match or read fails the call closed; the client reports `OutcomeUnknown`. See [DECISIONS.md](DECISIONS.md) D20. |
| A gateway config that fails open | check-config refuses `failOpen`, a missing decide header allowlist, a custodian header filter, stateful mode, a missing refusal guard, a missing or misplaced redactor, the wrong processor order, missing or unbounded upstream timeouts, a non-Unix processor target and an unsafe method surface. |
| A network observer reads a released credential or an agent's proof headers in transit | check-config refuses a gateway-bound upstream over `http` unless the host is loopback or a single-label service name, and a `backendTLS` with any key but `root`. The client and the stdio proxy refuse an `http` gateway url on the same terms. This is a stated trust assumption and a deployment limit, not a prevention control. The supported deployment is single host: gateway, bailiff and upstreams on one Docker host or machine. A plain-http single-label name is trusted to resolve inside that host's container network, so DNS on that network is in the trusted computing base. The check validates name syntax, not where a name resolves. Any hop that leaves the host must use `https://`; the check refuses dotted names and IP literals over `http`. Channel authentication (TLS on every non-loopback hop) is required before multi-host support and is tracked in #86. |
| A local user connects to a processor or the sink | Peer uid checks on every socket; processor sockets sit in a 0750 directory with the gateway's group. |
| Key or database file substitution | Key files and databases are opened with owner, mode, link and parent checks. The custodian re-checks its databases before each use. |
| A hijacked agent reaches the cluster with a catalog tool outside its approval | The effector rebuilds the request from the catalog and refuses unless the release, decide's clearance, the catalog digest, the arguments and the derived resource all agree. The admission webhook requires a valid 10 s release for the exact write and checks oldObject against object. The effector locally claims an op-id once and rejects releases predating its start; admission is stateless and cannot enforce either property. |
| A third-party MCP server or the agent obtains a cluster credential | No cluster credential is released. The effector's token never leaves the effector. |
| A compromised effector uses its token for other actions | Its service account can only impersonate the synthetic users and only for the catalog's calls in the tenant namespaces. Each synthetic user's own RBAC is limited to its identity's calls in its tenant's namespaces. Admission denies synthetic users every write outside the catalog's writes and their tenant's namespaces, replicas outside the range, a restart that changes anything but the two allowed pod template annotations bound to its op-id, and requests without one well-formed op-id. |
| An untrusted workload joins the release webhook Service | The webhook namespace is a trusted boundary: before Enforce, access review must establish that untrusted principals cannot create Pods or workload controllers, exec/attach/ephemeral containers, mount the TLS Secret, or mutate Services, Endpoints or EndpointSlices there. The webhook audit reports any serving endpoint that is not a Pod running the generated template (nested fields compared exactly after known defaults; scheduler fields and any pull secret names accepted; annotations not checked), any unconverged rollout, and access to Pod status, port-forward, `nodes/proxy`, service account tokens and mutating admission. In Enforce, two admission policies deny everyone but the deployer and the listed control-plane controllers writes to the namespace's workloads, Services, Secrets and RBAC and to the webhook registration, deny everyone exec, attach, port-forward, Pod and Service proxy and ephemeral containers, and let only control-plane controllers write Pods, ReplicaSets and endpoints and only a Pod's own node change its IPs. The deployer, anyone who can mint a controller, scheduler or node credential (for example by creating tokens or Pods in `kube-system`, impersonating those identities or approving a kubelet client certificate; the audit access-reviews the effector and Bailiff identities for those rights, including legacy and constrained impersonation of the deployers, controllers, serving nodes, `system:masters` and any user, group or node, while grants scoped to other names and other principals stay a manual review), `nodes/proxy`, mutating admission and changes to the policies themselves (exempt from admission policies; reported by the audit) remain outside the guard. |
| A grant widens the effector or a synthetic user, for example a legacy `impersonate` rule, a binding to `edit` or a grant to `system:authenticated` | Admission refuses bindings that name the effector, its audit account (also as a `system:serviceaccount:` user name) or a synthetic user, and RoleBindings to `system:authenticated` or the service account groups, unless the applier makes them. The drift check, at startup and 60 s after each check ends, compares the effector's and audit account's effective rules in every namespace, every synthetic user's catalog calls in its own namespaces, catalog grants to `system:authenticated` from other bindings, and every generated object with the generated set; any difference stops the effector. On GKE, where the rules review is incomplete, it accepts only the pinned evaluation error, and each account's own access review must deny a fixed list of dangerous actions. |
| Canary credential use | A canary release is refused, denies the task in the claims database and writes an alert entry. Control can then revoke the task. |

## Residual risks

These are known and accepted for the current release:

- **The upstream MCP server is trusted.** It receives the credential in the request. For `gateway-bound` credentials, the operation binding holds only at this layer.
- **Echo redaction covers only the call's own `tools/call` result.** agentgateway v1.7.0 runs no response processor on a JSON-RPC error or on an event-stream message other than the result (`notifications/message`, server-initiated requests). An upstream can put the credential in any of those. The bailiff client and the stdio proxy report a JSON-RPC error as `OutcomeUnknown` without its text and skip stream messages for other ids, so the model does not see them. Any client that reaches the gateway directly, the agent's own uid on the same host included, can read an echo carried in JSON-RPC error text or in an event-stream side message. Measured against the pinned v1.7.0 binary on 2026-11-26 (`tests/test_agentgateway_e2e.py`): a direct client gets the credential unredacted in the error `message` and in a `notifications/message` or `elicitation/create` sent before the result, no `credential_echo` alert is written, the redactor is called for the stream result only (not for the error or the side messages), and the gateway's stdout access log keeps the error text as `mcp.error.message` but not the side messages unless the config removes that field. check-config requires `frontendPolicies.accessLog.remove` to include `mcp.error.message` and refuses any other access-log setting, including `config.logging` keys other than `level` and `format`, and refuses `fields` under `config.tracing` and `config.metrics`; with it, the measured access line, in text and `json` format, has neither the field nor the credential. Other gateway stdout output, at any log level, and default trace and metric attributes were not checked, so operators must still treat the gateway's stdout as able to hold a released credential: restrict who can read it and bound how long it is kept. Agents must reach the gateway only through the client or the proxy; nothing on the network or the host enforces it.
- **Echo redaction is best-effort, not a containment boundary.** It suppresses the literal forms listed in D20, matched case-sensitively. A form shorter than 12 characters is not redacted, such as a short credential or a Basic password under 12 decoded characters, and neither is the password of a Basic token that does not decode to UTF-8. `put-credential` and the custodian refuse such a credential unless its owner stored it with `--accept-unredactable` (D22); the custodian then logs a warning at each release. The exception is bound into the row's encryption context but not to a version, so restoring an earlier complete row for the same binding, with write access to the store file, brings back that row's credential and exception. A short field inside a longer opaque token, such as one part of a multi-part API key, is neither found nor checked. A hex dump, re-wrapped base64, Unicode lookalikes, an echo split across JSON strings, or any other transformation (hashed, encrypted, reversed, re-encoded other than as listed in D20) is not found. The control against an upstream that leaks its credential is a short-lived, target-bound credential. Only the credential released for the call is matched, not one released for another call.
- **The in-flight release map is per custodian process.** A custodian restart between release and result, or a result that arrives after `inflight_ttl` (180 s by default, at least the 120 s upstream timeout cap plus 30 s), fails the call as `response_unmatched` after the upstream acted, and the client reports `OutcomeUnknown`. In the v1.7.0 tests, `requestTimeout`, `backendRequestTimeout` and `responseIdleTimeout` (1 s each) did not cut a 3.2 s event stream that sent a message every 0.4 s, so these timeouts do not keep a stream inside `inflight_ttl`; whether v1.7.0 has a whole-stream deadline was not checked. The custodian records the refusal as a `response_unmatched` entry under decide's entry when the clearance's signature verifies, even past its expiry, so the operator can find a call that acted upstream without a checked result. More than one custodian behind one gateway does not correlate releases with results.
- **Arguments outside a route's schema are not checked.** A route document's schema checks only the arguments that build the resource, such as `owner` and `repo`; the upstream MCP server gets the rest as the agent sent them and decides what they mean. A server that reads another argument as a different repository acts outside the scope decide checked, and arguments such as `issue_read`'s `output_path` reach it unchecked. The quickstart trusts gitea-mcp for this, as it trusts it with the released token.
- **A tool grant ending at `.*` covers tools routed later.** Tool grants are enforced exact or ending at `.*`, so `gitea.issues_*` is refused, but `gitea.issues.*` covers any tool routed later under `gitea.issues.`, across every separator: `x.*` covers `x.a_b`, `x.a/b`, `x.a-b` and `x.a:b` as well as `x.a.b`. Grant exact tools where the set must not grow.
- **Root is trusted.** Root can read keys, the credential store and the docket.
- **The docket is tamper-evident, not tamper-proof.** The sink uid or root can truncate or delete it. Signatures do not detect removed records; see [DOCKET.md](DOCKET.md) for writer-side rollback detection and its limits. The sink starts from a heads snapshot and checks only the SHA-256 of the records before it, so the sink uid or root can rewrite those records and the snapshot together and the sink still starts; a scheduled `docket verify --snapshot` with an alert on exit 1 is required to detect it, within the interval between runs.
- **A credential that has already been released lives until the upstream stops using it, and a completed effect is not undone.** A release that has passed the custodian's suspension check completes.
- **A compromised decide controls the ledger.** As the ledger owner it can drop revocations or alter reservations. The custodian's reservation check catches bugs, not a hostile decide. Its independent checks are the chain, leaf proof, binding table, claims and rate limit.
- **Control trusts pinned signers for bindings.** It revokes the root and link bindings named in a record signed by a pinned decide or custodian key, so a compromised signer can name any binding.
- **Docket report roles bind keys to hops, not to tenants.** One decide key serves every tenant, so a compromised decide key can write task rows, principals and counts for any tenant in `docket tasks`; a compromised custodian key can add rows, releases and refusals for any tenant; and a `--control-pin` key can mark any task revoked without a ledger change. ROOT `verified` says only that an allowed issuer signed the task root: a compromised custodian key can still add releases and refusals to a verified task, and a compromised decide key can write allows, a principal and a `record` under it. A grant writer can no longer list a task as `granted` or hand out its `record` without an issuer-signed root (ROOT `invalid`, exit 4), but its grants still open rows and count toward the budget. Any of them can fill the report's 1 GiB budget so that it refuses. Control itself checks no role. Binding control and custodian writers to tenants waits for per-tenant keys (#109); a decide record whose principal differs from the root's is not checked, a non-goal while one decide key serves every tenant. Use `docket grants --issuers` for the issuer-verified principal of a root.
- **There is no agent-key revocation across chains.**
- **An old record can be replayed to suspend again after a resume.** Control runs as decide's uid, and a replay only makes things more restrictive.
- **`--actor` is recorded as given.** It is not tied to the caller's OS identity.
- **One instance per writer and per custodian id.** A docket client locks its writer on its state directory, so a second instance on the same host and state fails to start. Instances on separate state directories or hosts are not detected. Two custodians with one id and separate claims databases can each claim, and release, the same clearance; custodians sharing one claims database claim each op_id once. Run one custodian per id with one claims database, and one instance per docket writer name.
- **The per-task rate limit is in memory.** A custodian restart resets it. It tracks at most 65536 live tasks; while that many are live, a release for a new task is refused as `rate_limited`, and checking it scans the tracked tasks.
- **A captured live effector release can be replayed at admission until the webhook's clock reaches its expiry, at most 10 s after issue.** The skew bound (0 to 2 s) only admits a release issued that far ahead of the webhook's clock, so the window is never longer than 12 s; a webhook clock behind the custodian's moves it later by the lag without lengthening it, so a captured release stays replayable until that long after its expiry. It can undo an intervening write, and suspension does not invalidate an already issued release at admission. This requires access to a live release and an effector-capable token (host compromise is one route). A stolen effector token alone cannot construct a valid release. Reduce the exposure through the short lifetime and synchronised clocks; do not represent this as cluster-side single-use.
- **The revocation tables only grow.** There is no retention.
- **Directory checks read mode bits, owner and group.** They do not inspect ACLs, and they check only the immediate parent directory. The ledger's parent check, in agent-warrant, does not check the parent's owner.
- **check-config runs at startup only.** agentgateway reloads its config on change, so the config file must be writable only by a user that is neither the gateway's nor an agent's.
- **agentgateway v1.7.0 runs no processor for client notifications.** They reach upstreams with every agent header except the ones `requestHeaderModifier` removes, including the `x-bailiff-*` headers and any identity header the agent adds. See [AGENTGATEWAY.md](AGENTGATEWAY.md).
- **`_meta` values in `tools/call` are not bound to the proof.**
- **Reconciliation depends on decide's clock.** It moves an operation to `outcome_unknown` once decide's clock passes the clearance expiry. If the custodian's clock is behind, it refuses that operation as no longer issued; this fails closed. Keep the hosts' clocks synchronised.
- **A reconcile entry for an operation this decide issued can be lost.** For those, the ledger changes before the entry is written, so a docket failure at that moment leaves no entry. Operations found only in the ledger are written to the docket first, under a trace id derived from the op_id; a retry after an unacknowledged append can write that entry twice under the same trace id. If such an operation is reported done while its entry is being written, the docket holds both an `outcome_unknown` entry and the outcome; the ledger state is authoritative.
- **Decide and custodian lifetimes are not checked against each other.** If decide's `max_proof_age` is above the custodian's `max_clearance_lifetime`, decide records an allow that the custodian then refuses as `clearance_invalid`. `init` writes equal values.
- **Unrecorded refusals.** Decide and custodian refusals before verification (`malformed_request`, `chain_invalid`, and an `internal_error` before the chain verifies) are logged, not docketed, so an unauthenticated caller cannot grow the docket. One exception: when the custodian verifies decide's clearance, checks that the request is the one the clearance names and then refuses the chain, it records `chain_refused` with the handles from the clearance, and the caller sees `release_refused`. A forged clearance, or a request that does not match the clearance (`clearance_mismatch`), records nothing. The redactor records `response_*` refusals only for a call whose release it holds or whose clearance verifies; a missing or unverified clearance is logged only. It records `response_unmatched` once per operation in the same way as `chain_refused`. The custodian records each operation's `chain_refused` once while it holds that operation among its last 65,536 recorded refusals, in memory, so a restart or eviction within the clearance lifetime can record it again. It also tries again after an append the docket did not acknowledge, which can record it twice; once the sink acknowledged the entry it does not try again, even if the client then fails to save its head. The custodian records `already_issued` and `task_denied` once per operation in the same way. For all three, an identical refusal that arrives while the first one's append is still in flight is not appended. If the docket then refuses that append outright (for example `overloaded` at its connection cap or `docket_full` at its free-space floor), neither is recorded until a later identical refusal arrives. The first one logs a `was not written` warning naming the tenant, task, op and reason; the second logs only the gateway processor's `custodian processor refused a release` line with the caller-facing reason (`chain_invalid` for `chain_refused`) and, for `chain_refused`, the custodian's `custodian refused the chain` line with the library reason. Neither names the tenant, task or op. Nothing is released either way. The agent holding the clearance can send its own request with a broken leaf proof, so a `chain_refused` entry does not show that the operation was never released. `chain_invalid` includes calls on a revoked or expired task, so a revoked agent's later attempts leave only log lines. Decide keeps two refusal budgets per task root in a 60 s monotonic window: one for reasons the agent's request causes (`out_of_scope`, `unknown_cost`, `cost_over_call_cap`, `no_binding`, `policy_denied`, `needs_approval`) and one for every other verified reason (suspension, ledger, docket, internal errors, `already_*` replays). Each records 16 refusals, then one marker with the task's handles (`refusals_capped` or `operational_refusals_capped`), then only logs. Padding with refusals of either class cannot hide an agent-caused refusal: either it is recorded or `refusals_capped` is, and the quickstart rule revokes on `refusals_capped` only, so a suspension, an outage or a replayed request does not revoke a task. `no_binding` and `unknown_cost` can also come from an operator's binding or cost table gap, so an agent that retries such a call 17 times in 60 s is revoked. A refusal counts unless the docket client reports that it was not written (the sink was unreachable or refused it); a lost or mismatched acknowledgement, or a failed sink write, counts. Decide tracks at most 4096 windows per tenant and 65536 in total. A refusal it cannot track is recorded as `tenant_refusals_capped` once per tenant per window, with a warning log, for at most 65536 tenants at once, and otherwise only logged. That marker names the task that hit the limit, not a culprit, so the rule does not revoke on it. Residuals: each root can hold two windows, so an attacker who holds 2048 issued task roots in one tenant (or 32768 in total) and keeps both windows refusing in every window can hide a new task's first refusal behind the tenant marker, which tells the operator that the records are incomplete. Each root can produce up to 34 records per minute, and the sink has no per-tenant share of its fsync throughput. The quickstart rule revokes at task level, so if an issuer gives two roots the same task id, an out-of-scope call under one root revokes the other root's task too; `docket grants` flags granted roots that share a tenant and task id in `duplicate_roots`. Windows are in memory and reset on restart, and the clock must be monotonic. The log line for an unverified refusal is written per request; bounding that rate belongs to the gateway. Control applies its action before recording it and reports an unacknowledged entry as unrecorded.
- **v1 scopes are accepted until the cutoff.** A root with a v1 scope, which pairs every listed tool with every listed resource, is accepted when issued before `scope_v1_cutoff`. The issuer sets `issued_at`, so an issuer key can still mint a v1 root with free pairing, backdated, until the cutoff; a root lasts at most 86,400 s, so none is accepted after the cutoff plus that. `init` writes 0, which accepts none. Decide logs each accepted v1 root as a `scope_v1_accepted` warning with its root binding; the docket does not record the scope version, so docket entries before the cutoff plus 86,400 s are the v1 candidates.
- **Decide and custodian cutoffs are not checked against each other.** If the custodian's `scope_v1_cutoff` is earlier than decide's, decide allows and reserves a v1 call that the custodian then refuses; it records that as `chain_refused`. Both services log their effective cutoff at startup. Set them equal; see [UPGRADE.md](UPGRADE.md).
- **A scope must fit a 4,096 B task file.** agent-warrant allows 16 permissions and 64 entries, but the task file holds at most 4,096 B. `task issue` refuses a larger scope before signing, so the limit shows at issue, not on a call. Two permissions over 20 repositories make a 1,670 B task file, and 16 single-pair permissions 2,738 B.
- **Spans are a view, not evidence.** A collector or trace backend can drop, alter or invent spans without a writer key, and holds what docket readers see. Decide, the custodian and the effector all record the trace id from the agent's `traceparent`, which the leaf proof does not bind, so an agent can place its records in any trace, including another task's. The effector also sends it to the Kubernetes API as the `bailiff.dev/trace-id` impersonation extra, so audit joins on that extra are agent-controlled too. Use `docket verify` to establish what happened.
- **An automated revoke rule has control's authority.** It runs as decide's uid and can read decide's signing key, like control. It acts only on the signed fields it matches; anything it does not match is not revoked.
- **The docket sink writes and fsyncs on its event loop.** A slow disk delays every writer, and writers then refuse calls when their append times out.
- **A full docket file system stops calls.** Below `free_space_floor` the sink refuses appends with `docket_full`, so decide refuses every call and the custodian releases nothing until space returns. Any process that can write to that file system, including an allowed writer appending at its full rate, can bring it there, and one tenant's writes stop every tenant. Calls refused while the docket is full leave no signed record and do not count toward an agent's refusal budget, so probes made then are not seen by revocation rules. Sealed segments are removed only after an archive receipt, so a stopped or slow archiver lets the docket grow to the floor; see [DOCKET.md](DOCKET.md), Disk full and Removal.
- **The archiver uid and the receipt directory are trusted for removal.** A receipt that matches a segment's manifest entry lets the sink delete it. The archiver uid, or anyone who can write the receipt directory, can write such a receipt without an archived copy, and the sink then removes records that exist nowhere else. Receipts guard against an archiver bug or an archive that was lost or changed, not a hostile archiver uid. The sink opens the directory from its config and checks only its owner, group and mode, and refuses an `archiver_uid` equal to its own uid. `agent-bailiff docket run` also refuses to start with euid 0, which could write the receipt directory itself. It checks only the euid: a sink with a real or saved uid of 0, or holding `CAP_DAC_OVERRIDE`, `CAP_FOWNER` or `CAP_CHOWN`, can still write it, so run the sink without those.
- **A receipt vouches for the archive only when it was written.** The archiver rechecks copies every `--refresh-interval`; a copy lost after its last recheck still lets the segment be removed until the receipt is `max_receipt_age` old. The archive's device is checked against the docket's, not its host. Before each receipt the archiver checks that the archive directories at their paths are still the ones it opened, so a remount stops it rather than vouching for a detached copy. That check is not atomic with the write: anyone who can rename entries in the archive directory's parent can still swap a directory in between. Keep that parent writable only by root or the archiver uid.
- **Readers keep removed segments on disk.** A reader with a removed segment open keeps its blocks allocated until it closes it, so a slow `docket verify` or exporter holds space that removal freed in the manifest only.
- **Processor relays have no idle timeout.** Idle connections can hold the 64-connection cap; see [AGENTGATEWAY.md](AGENTGATEWAY.md).
- **Python cannot reliably zero secrets in memory.**
- **A task root is bound to its agent's key only if the agent's uid cannot reach the issuer.** Decide checks `covers` on every call, spend per task and revocation at root, link, task and tenant level, and a task root is bound to the agent's public key. An agent that can use the Docker daemon or read the issuer key or the custodian's key encryption key and credentials can mint its own root or read the service credential, and none of those checks apply. Run the agent as a uid with no Docker access and no read on the issuer key, and run `task issue` as the operator; the agent receives the task root and its own key as files. A single-user host where the agent owns the Docker socket does not meet this. `agent-bailiff proxy run` detects at start that its user can reach a Docker daemon: a listener, or an existing socket the user can write to, at `DOCKER_HOST` (when `unix://`), `/var/run/docker.sock` or the usual per-user locations under `$HOME`, the passwd home, `$XDG_RUNTIME_DIR` and `/run/user/<uid>`, or a `DOCKER_HOST` that is not a `unix://` URL. A writable socket with no daemon counts, because a daemon that starts later grants Docker. `--allow-shared-user` skips the refusal for development and prints a warning. The check is a start-time guard against misconfiguration, not a boundary. It does not see a socket path it does not probe, including rootless sockets elsewhere and a `DOCKER_HOST` that names a socket reachable by another path, a Docker context (`DOCKER_CONTEXT`, `currentContext`), a group membership or `sudo` granted after start, or a route to the issuer key that does not use Docker, and it does not check the issuer key itself, whose host path the proxy cannot know. An agent that is not started through `proxy run` is not checked. The MCP host config that launches the proxy must not be writable by the agent user; otherwise the agent can add `--allow-shared-user` or change the environment the check reads.
- **The gateway's published port is reachable by every local user.** The quickstart publishes it on `127.0.0.1` only, so no other host reaches it, but any process or user on the host can connect. The task root and the per-task key gate calls, not the port. The gateway also joins a non-internal `egress` network to reach https upstreams, so the gateway container has outbound network access.
- **Gateway egress has no destination filter.** The `egress` network lets the gateway reach any address its host can reach. Its config names one upstream, and it does not follow redirects. Bootstrap refuses an upstream URL that names one of the stack's own components, `localhost`, or a loopback, link-local, unspecified or multicast IP address written in standard form. It does not refuse private ranges, other spellings of an IPv4 address such as `2130706433` or `0x7f000001`, which Python's `ipaddress` treats as hostnames, or a hostname that resolves to such an address, now or after a DNS change. The upstream config is the operator's; an agent cannot change it.
- **`ca_file` replaces the gateway's system roots for the upstream.** With `ca_file`, bootstrap sets agentgateway's `backendTLS.root`, so the gateway trusts only those certificates for the upstream. Whoever holds that CA's key can issue a certificate for the upstream's name, and a server presenting it on a path the gateway reaches receives every released credential.
- **The gateway runs without a session key.** agentgateway v1.7.0 logs `no session key configured; MCP session IDs are not encrypted` at start, because its config file is read-only and it cannot write the key it generates. check-config requires `statefulMode: stateless`. What an unencrypted session ID exposes in stateless mode has not been assessed.
- **A copied task root and agent key stay valid until the root expires.** Renewing a task issues a new root and does not revoke the old one; the old root is valid until its TTL (default 1 hour) or a manual revoke. Revoke by task through `docket tasks --json` and `control revoke --level task`. A task that never made a call is listed from its grant and revoked from it; a root signed without a grant is listed only once it is used.
- **Grants are evidence, not enforcement.** Decide does not look for a grant before it allows a call, so a missing grant blocks nothing. A holder of the issuer's task root signing key, the issuer host's root and uid included, can sign a root and record no grant, as can an issuer still on an earlier release. Such a root is detected only after the fact, and only if it is used: `docket grants` lists it as `ungranted`. A root that is never used, and a grant in a segment removed from the host, are not seen. Checking for a grant at decide was rejected: it puts a docket read on every call and adds a refusal mode.
- **The issuer's docket-writer key does not shrink the issuer's blast radius.** It is separate from the task root signing key so that either can be rotated without the other. Both sit on the same host under the same uid, so whoever takes one can take the other.
- **Control trusts a grant writer for revocation after checking the root.** It revokes from a grant only when the grant's writer is a pinned grant writer, the root verifies against an issuer key in control's `issuers` and that issuer's allowance covers the root's tenant, principal, budget and depth. It does not check the root's expiry. Control's `issuers` is a copy of decide's that the operator keeps in step; an issuer left in it after decide drops it can still revoke from its grants. A holder of the issuer's keys can sign a root that reuses another task's id, record its grant and revoke that task, or revoke a whole tenant, within the tenants the issuer may issue for. That is denial of service, not a widening of access; the same holder can already issue tasks there.
- **A grant can name a root no agent holds.** If the acknowledgement of the append is lost, or the process dies between the append and the rename of `task.json`, the grant can be recorded with no `task.json` written. The root stays in `task.json.pending` and is valid until it expires. `task issue` names the `grant_id` when the outcome is unknown; find the root with `docket grants`, where every pair shows unused, and revoke it from its grant.
- **`task issue` needs the docket.** It records the grant before it writes `task.json`, so with the sink down, refusing or full, no task is issued. The issuer must reach the sink's Unix socket from the sink host; issuing from another host is not supported.
- **`task issue --out-dir` checks only the final directory.** It opens it with `O_DIRECTORY` and `O_NOFOLLOW`, and requires the operator's euid as owner and no group or other write bit. `O_NOFOLLOW` covers only the last component, so a symlink or rename in an ancestor that another uid can write redirects the task file. Place the task directory under a path no other uid can rewrite, with every ancestor owned by the operator or root.
- **Upstream tool titles and descriptions reach the model.** The proxy's `tools/list` passes `name`, `title`, `description` and `inputSchema` of routed tools, dropping a tool whose title or description is not a string of at most 4096 bytes or whose schema is over 16384 bytes or nested deeper than 32. The text is not otherwise sanitised, so a hostile or compromised upstream can inject instructions. The task root's scope is the control: it must tolerate every call the instructed agent can make.
- **ClusterRoleBindings to `system:authenticated` or the service account groups, and grants through other groups, are detected, not prevented.** A grant by a non-RBAC authorizer to every authenticated user is not detected. A direct RBAC or admission change is in effect until the next drift check finds it, up to 60 s plus the duration of a check, unless the binding policy refuses it. The admission objects themselves are protected only by the drift check.
- **On managed clusters, read-only is a property of the catalog and the generated RBAC, not proof.** Privilege granted outside RBAC is audited residual risk. On GKE a cloud IAM grant to the effector or audit account outside the dangerous-action list is not seen by the drift check, only by the runbook's cloud IAM check, run on a schedule. On GKE 1.36.4 a project `roles/container.developer` grant to a service account's Workload Identity principal did not authorize that account's own Kubernetes requests within 11 minutes; other roles and bindings were not tested. On EKS, nothing has been probed.
- **The GKE pin identifies the authorizer type, not its identity.** The accepted evaluation error is upstream Kubernetes' generic webhook authorizer text.
- **Anyone who can mint the effector's tokens holds the effector's cluster power.** That includes the minter, RBAC holders of `create` on `serviceaccounts/token` in the effector namespace, GKE principals with `container.serviceAccounts.createToken` (in `roles/owner`, `roles/container.admin` and `roles/container.developer`, project-wide) and EKS principals with a cluster-admin access policy or `system:masters`. The drift check reviews only the effector's and audit account's own grants, so it does not list these principals. A minter on the effector host would let whoever takes the host mint more; mint off the host.
- **The drift check's rules reviews grow with the cluster's namespace count.** Past 120 s per check, every call is refused. The dangerous-action reviews are bounded by the configured namespaces. Durations on GKE have not been measured.
- **Admission does not see reads.** Effector reads are bounded by the impersonate-on grants and the catalog.
- **Pod logs reach the agent unchanged.** They are untrusted input that can carry instructions, and a secret an application logs is exposed to the agent and anything it calls. Scope bounds what an instructed agent can do; nothing stops the secret leaving.
- **A cluster credential for a `bailiff:` user name acts with that synthetic user's grants.** Issuing one needs control of the cluster CA or identity provider.
- **One effector instance.** Its single-use set is in memory.
- **In Audit mode, or when the release webhook is absent, a stolen effector token can restart and scale any Deployment in tenant namespaces, repeatedly.** The effector itself refuses writes until its drift check sees the webhook registered fail-closed with a Service that selects only Enforce-mode pods (whether such pods serve, and with which CA, is the webhook audit's check), but the token works without the effector. In Enforce mode, each write also needs a valid release for its exact change. A captured release remains replayable until the webhook's clock reaches its 10-second expiry, and can undo an intervening write.
- **The restart policy compares a fixed list of fields.** When the cluster's Deployment schema differs from that list, the drift check withdraws restart from the effector. After an upgrade that adds a Deployment or ObjectMeta field, a stolen effector token can change that field through the restart identity in Audit mode or when the release webhook is absent, until the policy is regenerated.
- **A restart follows the Deployment's strategy.** Under `Recreate`, or `maxUnavailable` at least the replica count, it is an outage. Rollouts do not consult PodDisruptionBudgets.
- **A stolen audit token reveals the cluster's RBAC and admission layout.** It lists them cluster-wide.
- **A network peer that can reach the release webhook can exhaust its connection slots.** Each connection is cut after 5 s, but repeated connections still deny bailiff writes in Enforce and hide them from `would_deny` in Audit. Ingress must be restricted to the API server on the target cluster; this is not generated.
- **Other admission webhooks and API audit-log readers see the release extra** and can replay a released write within its lifetime.
- **The release webhook namespace is a trusted boundary.** A principal who can create a Pod there may mount the serving TLS Secret and spoof the Service selector. The webhook audit reports a serving Pod that differs from the generated template, but only when it runs, and it does not enumerate all principals or prove who created a Pod. Enforce requires a dedicated restricted namespace (the generators refuse `default` and `kube-*`), an effective access review across principals/groups, and a scheduled audit. The namespace guard denies such Pods at admission in Enforce, but it trusts the deployer and every holder of a controller, scheduler or node credential (a cluster admin can mint one), does not cover `nodes/proxy` or mutating admission, and cannot protect its own policy objects, which Kubernetes exempts from admission policies.
- **The effector's op-id in Kubernetes audit events is unverified.** It is sent as an impersonation extra.
- **On macOS, `fsync` does not flush the drive cache.**
