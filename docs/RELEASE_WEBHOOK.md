# Release-verifying admission webhook

The release webhook adds cluster-side verification for Bailiff's catalog writes. Kubernetes admission receives `bailiff.dev/release` and `bailiff.dev/op-id` as impersonation extras. It checks the signed release and decide clearance with the same pure verifier used by the effector, binds the complete user/verb/resource/subresource/operation/kind and arguments to the release, and compares the old and new objects. A captured live release remains replayable until its 10 second lifetime plus the configured clock skew; suspension does not revoke a release already issued. A stolen effector token alone cannot create one.

## Actionable feedback

The webhook writes one-line JSON events to stdout for log collection:

- `bailiff_admission_would_deny`: a request that would fail verification while the webhook is in Audit mode. The request is allowed in this mode.
- `bailiff_admission_denied`: a request rejected in Enforce mode.
- `bailiff_admission_invalid_request` and `bailiff_admission_internal_error`: the webhook could not evaluate a valid request. The registration uses `failurePolicy: Fail`, so API writes fail closed.

Denial events include `reason_code`, `mode`, AdmissionReview `request_uid`, username, operation, resource, subresource, namespace and name. They never include the release, op-id, request object, or exception text. Route both denial event names to the Kubernetes security/on-call log alert path. In Audit mode, alert on `bailiff_admission_would_deny`; in Enforce mode, alert on `bailiff_admission_denied` and the two availability events. Retain Kubernetes API audit events long enough to investigate the request UID and impersonated identity. Kubernetes audit events can include the impersonated `UserInfo`, which has an `extra` map; verify whether the release extra is recorded by the target provider and restrict audit-log readers accordingly. Treat a recorded live release as a short-lived write capability. Do not treat webhook stdout as a durable audit ledger.

For an unexpected denial or would-deny:

1. Use `request_uid`, username and resource coordinates to find the matching Kubernetes API audit event and the authorized Bailiff operation/release record.
2. If the write was expected, identify the precise mismatch and correct the release, identity, object change or generated policy before enabling Enforce.
3. If it was not expected, suspend the task/tenant through Bailiff control, revoke the effector token, preserve webhook/API audit logs, and investigate the effector host and signing chain. Rotation of custodian and decide keys follows the documented key-rotation procedure.
4. If the webhook itself is unhealthy, keep `failurePolicy: Fail`; as a deployer, apply the generated manifests with `--enforce` omitted to roll back to Audit mode, investigate, and rerun the audit. Do not delete the ValidatingWebhookConfiguration as a rollback: that silently removes the gate.

The `agent-bailiff-webhook audit` command checks generated webhook resources against live objects and runs SubjectAccessReviews for the Bailiff identities and effector account. It requires the full manifest set (the Audit bundle, or the Enforce `--phase target` output) and refuses a `prepare` or `register` phase, which would omit objects. It also reports a Deployment whose rollout has not converged, no ready endpoint, and any EndpointSlice endpoint of the webhook Service that is not a Pod in the webhook namespace running the generated template at its own Pod IP. The Pod spec, including every nested container, port, probe, resource, affinity, volume mount and volume field, must equal the template after the Kubernetes defaults the audit knows (pod defaults, container termination message, probe thresholds and timeout, port `protocol: TCP`, volume `defaultMode: 420`). The only other fields accepted are those the scheduler and admission set: `nodeName`, `priority: 0`, `serviceAccount` equal to `serviceAccountName`, the default `not-ready`/`unreachable` NoExecute tolerations, and any `imagePullSecrets` names, which ServiceAccount admission copies from the service account (the image is pinned by digest, so a pull credential cannot change what runs). Anything else, such as `args`, `env`, `hostPort`, a probe `host`, extra resources, `hostAliases`, `dnsConfig`, `runtimeClassName`, a service account, an extra volume, `subPath` or init containers, is reported. Pod labels must include the template's; Pod annotations are not checked. The audit cannot tell who chose `nodeName`. On a cluster with a default PriorityClass or other default tolerations, the audit reports drift; review those fields before accepting them. The same rule applies to the Deployment's pod template, and Deployment fields beyond the generated ones and the API defaults, such as `paused` or `minReadySeconds`, are drift. The audit also reports a webhook namespace that is the effector's or a tenant's. This is a point-in-time check: a Pod created after an audit is seen only by the next run. Each finding names the drifted object, endpoint or excessive permission and gives the immediate remediation. The audit runs as the effector's audit account. The effector's generated RBAC (`agent-bailiff effector manifests --webhook-namespace`) grants that account get on Pods and list on EndpointSlices in the webhook namespace only, and the effector's drift check owns that grant. Run it during deployment and on a schedule; a nonzero exit is a deployment gate. This repository emits the structured events and actionable audit results, but paging, retention and scheduled audit execution must be connected to the cluster's log/alert and deployment systems.

## Namespace and registration guards

`agent-bailiff-webhook manifests` requires `--deployer`, repeated for each user allowed to change the webhook's objects, normally the GitOps applier. The output includes two ValidatingAdmissionPolicies with bindings, in the same mode as the webhook: `Audit` and `Warn` in Audit mode, `Deny` in Enforce. Both use `failurePolicy: Fail`.

- `bailiff-release-webhook-namespace`, bound to the webhook namespace only, covers create, update and connect on Pods, Pod binding, resize and status, ephemeral containers, exec, attach, port-forward, Pod and Service proxy, Services, Endpoints, EndpointSlices, Secrets, ConfigMaps, ServiceAccounts and their tokens, ResourceQuotas, LimitRanges, NetworkPolicies, workload controllers, PodDisruptionBudgets, Roles and RoleBindings. It denies everyone, including cluster admins and the deployer, exec, attach, port-forward, `pods/proxy`, `services/proxy` and ephemeral containers; the proxies would otherwise reach the webhook port from the API server, which an API-server-only ingress rule cannot tell from admission calls. It denies creating StatefulSets, DaemonSets, Jobs, CronJobs and ReplicationControllers. Pods, ReplicaSets, Endpoints and EndpointSlices may be written only by the controller manager, and only the scheduler may bind a Pod to a node. Status may be written only by named control-plane controllers or the Pod's own node, and only the Pod's own node may change a Pod's IPs. Every other covered write must come from a deployer or one of the listed controllers: the guard does not limit a controller identity to the resources that controller manages, so for those identities only RBAC applies. Controllers are matched by exact user name in both forms, `system:kube-controller-manager` and `system:serviceaccount:kube-system:<controller>`, so the guard works with or without `--use-service-account-credentials`. Deletes and Pod evictions are not covered: deleting or evicting a Pod (eviction is bounded by the PodDisruptionBudget) or deleting the Deployment can deny service, but cannot make an attacker's Pod serve. Changes outside the namespace that only deny service, such as node taints, are not covered either.
- `bailiff-release-webhook-registration` denies creating, updating or deleting the ValidatingWebhookConfiguration `bailiff-release-webhook` by anyone except a deployer. Kubernetes does not run admission webhooks on webhook configurations, but it does run admission policies on them.

The generator refuses a deployer that is anonymous, unauthenticated, a control-plane or node identity, a `kube-system` service account or a service account in the webhook namespace, or that contains a quote, backslash or newline.

The guard trusts user names, so its trust root is everyone who can obtain one of the trusted identities: a deployer, the listed controllers and the scheduler, and the nodes. That includes anyone who can impersonate those users or service accounts, create service accounts, tokens or Pods in `kube-system`, read Secrets there, or get a control-plane or node client certificate. On most clusters cluster admins hold these rights, so in Enforce the guard stops a cluster admin's direct writes and streaming, not a cluster admin who sets out to mint a controller credential; a reproduction on kind created a serving Pod with a minted `replicaset-controller` token. The webhook audit's access reviews check that the effector and the Bailiff identities cannot create service accounts, tokens or Pods in `kube-system`, get, list or watch its Secrets, or approve kubelet client certificates, and cannot impersonate any user, group or node, the trusted controllers, the deployers (read from the manifest's guards, which must match the generated guards), the nodes currently running webhook Pods, or the `system:nodes` or `system:masters` group. A review without a name matches only grants that are not limited by `resourceNames`, so a grant to impersonate another named group, such as one bound to `cluster-admin`, stays a manual review. Impersonation is reviewed in both modes Kubernetes authorizes it in: the legacy `impersonate` verb in the core group and the constrained `impersonate:user-info`, `impersonate:serviceaccount`, `impersonate:arbitrary-node` and `impersonate:associated-node` verbs in `authentication.k8s.io`. A node that runs a webhook Pod only after the audit is reviewed on the next run, so a grant to impersonate a node that does not yet run one is not reported; pinning the webhook to a dedicated node pool and reviewing that pool would close this, and is not implemented. Every other principal stays a manual review. Anyone who can change the guards can also change the webhook. Kubernetes exempts ValidatingAdmissionPolicies and their bindings from admission policies, so the guards cannot protect themselves; the webhook audit reports any change to their specs and access reviews showing that a Bailiff identity or the effector can write them. Grant write on these four objects to the deployer only. A user who can disable the `ValidatingAdmissionPolicy` admission plugin or reach the kubelet API (`nodes/proxy`) is outside this guard. The webhook audit's account reads the guards by name; `agent-bailiff effector manifests` grants it.

In Audit mode, warnings appear on the client and as `validation.policy.admission.k8s.io/validation_failure` annotations in the API audit log. Before Enforce, collect that evidence for the observation window: a legitimate write that would be denied, such as a different controller identity on a managed control plane, shows up there. Then probe as a cluster admin, for example `kubectl -n <webhook namespace> exec deploy/bailiff-release-webhook -- true` and `kubectl -n <webhook namespace> run probe --image=<pinned image>`, and confirm both return the guard's warning.

The cluster test `tests/test_webhook_guard_cluster.py` covers controllers running, restarting, replacing and scaling the Deployment under `Deny`; a cluster admin denied 22 writes including exec, attach, debug, Pod and Service proxy, a Pod, a Job, a Pod binding and resize, a quota, a NetworkPolicy, a Service selector change and deleting the registration; a forged Pod IP from the node controller; Audit mode warning but allowing; the generated specs round-tripping unchanged; and, with `AGENT_BAILIFF_TEST_NODE_LOSS_CONTAINER_RUNTIME` on a multi-node kind cluster, a worker loss followed by rescheduling. It passed on OrbStack (k3s v1.36.5) and a three-node kind v1.36.4 cluster. When `kubectl exec` used impersonation on OrbStack, admission saw the caller rather than the impersonated user; the exec rule denies all users, so the result did not change.

## Rollout and operational gates

1. Generate and apply the full webhook in Audit mode. Route the `would_deny` event to the on-call path and observe legitimate writes through a representative workload window.
2. Require a clean `agent-bailiff-webhook audit`, a successful TLS load/abuse test, and a reviewed API audit-log sample proving release extras are not exposed to unauthorized readers.
3. Verify admission transport limits and audit visibility on the target managed Kubernetes provider. OrbStack's successful 16 KB probe does not establish DOKS behavior.
4. Use a dedicated, access-restricted namespace for the webhook. Verify by access review that Bailiff identities and the effector account cannot mutate the webhook registration/CA bundle, pins, TLS Secret, Deployment, or namespace. Also review every effective principal and group: untrusted principals must not be able to create Pods/workloads in the namespace, use `pods/exec`, `pods/attach` or ephemeral containers (reviewed for both `create` and `get`, since clusters before the websocket authorization change authorize streaming with `get`), or mutate Services, Endpoints, EndpointSlices, Pod status or the TLS Secret, port-forward or proxy to Pods or the Service, use `nodes/proxy` (which reaches the kubelet's exec and attach without admission), mint service account tokens, or create mutating webhooks or mutating admission policies, which can rewrite the webhook's Pods. A Pod creator in this namespace can mount its TLS Secret and match the Service selector. `agent-bailiff-webhook audit` runs these access reviews in the webhook's namespace, read from the manifest, for the effector and each synthetic user (the effector's grants to impersonate the synthetic users are checked by the effector's drift check; impersonation of anyone else is reviewed here, see the guards section). Grants limited by `resourceNames` are reviewed for the names the audit knows: the Service's proxy names in every form RBAC matches (`<name>`, `<name>:<port>` and `<scheme>:<name>:<port>`, by port number and name, with and without a port), and, for each Pod serving the webhook, Pod updates, status, ephemeral containers, exec, attach, port-forward and proxy in the same forms. A grant scoped to a Pod name that does not serve yet is reported only once it serves. The audit also reports the webhook namespace if it is also a tenant namespace, and verifies that each serving endpoint runs the generated template. It does not establish who created a serving Pod (a Pod creator can set its own owner references), and the review of every other principal and group stays manual. The namespace guard enforces most of this at admission; in Enforce mode a cluster admin's direct writes are denied: creating a Pod or workload, exec, attach, port-forward or proxy in the namespace, or changing its Services, Secrets or the registration (see the guards section). It does not cover `nodes/proxy`, mutating admission, the deployer, or anyone who can mint a controller, scheduler or node credential. The generators refuse `default` and `kube-*` as the webhook, effector or tenant namespace.
5. Switch to Enforce in two phases; never apply a full Enforce bundle in one `kubectl apply`:

   ```sh
   agent-bailiff-webhook manifests ... --enforce --phase prepare > enforce-prepare.json
   kubectl apply -f enforce-prepare.json
   kubectl rollout status deployment/bailiff-release-webhook -n bailiff-webhook
   agent-bailiff-webhook manifests ... --enforce --phase target > enforce-target.json
   agent-bailiff-webhook manifests ... --enforce --phase register > enforce-register.json
   kubectl apply -f enforce-register.json
   agent-bailiff-webhook audit --manifest enforce-target.json ...
   ```

   First require a clean Audit-mode audit and the external gates above. The prepare phase updates the pinned mode config and pod template, triggering a rollout; pods carry the label `bailiff.dev/webhook-mode`. The register phase switches the Service selector to `bailiff.dev/webhook-mode: enforce` together with `failurePolicy: Fail`, so an Audit-mode pod can never serve a review under Fail; if no Enforce pod is ready, bailiff writes are denied rather than allowed. Wait for `kubectl rollout status` to complete before registering: `manifests` renders offline and cannot check the rollout, so this step is the operator's; registering early fails closed. The audit against the target then checks the rollout and every serving endpoint. `--phase target` renders the full Enforce desired state as a `WebhookAuditTarget`, which `kubectl apply` refuses; use it only with `audit --manifest`.
6. Keep the alert route and recurring audit active. Apply every bundle, and run the rotation and rollback below, as a deployer: in Enforce the guards deny anyone else. If the deployer is unavailable, break glass with an audited cluster-admin identity: delete the two guard bindings (admission policies cannot block that), make the change, apply the generated guards again as soon as the deployer is back, and require a clean webhook audit before returning to normal operation. Record each break-glass use; the audit reports the missing bindings until they are restored. To roll back, first render/apply the Audit registration (`manifests ... --phase register`), which sets `failurePolicy: Ignore` and returns the Service to selecting every webhook pod, then render/apply the full Audit bundle and wait for the Audit-mode rollout. Never delete the registration as rollback.

The webhook uses TLS 1.2 or later, a concurrency limit, request-size limit, socket timeouts and an absolute 5 s deadline per connection, including the TLS handshake, so a slow client cannot hold a slot. A peer that keeps opening connections can still fill the slots: in Enforce that denies bailiff writes, and in Audit it admits them with no `would_deny` event. Restrict ingress to the webhook port to the API server with a NetworkPolicy or the provider's equivalent; how the API server and kubelet probes reach Pods depends on the CNI, so this is not generated and must be verified on the target cluster. Any other admission webhook, and anyone who reads API audit logs, can see the release extra; treat both as able to replay a released write within its lifetime. The serving private key is mounted from a Secret and is not embedded in generated manifests. The Service must keep `publishNotReadyAddresses` unset or false; the drift audit reports it if enabled because it bypasses mode-aware Pod readiness. Serving certificates expire after 90 days. Rotate before expiry with an overlapping CA bundle, running each apply and restart as a deployer. A controller that writes the TLS Secret, such as cert-manager or External Secrets, must be passed as a `--deployer` and is then part of the trust root:

1. Generate a fresh certificate set in a new protected directory; keep `ca.key` offline.
2. Concatenate the old and new CA certificates into `ca-overlap.pem`. Render and apply only the registration, passing this bundle to `--ca` (and `--enforce` if Enforce is active). This keeps the current serving certificate trusted while adding trust for the replacement.
3. Update the TLS Secret and roll the pods:

   ```sh
   kubectl -n bailiff-webhook create secret tls bailiff-release-webhook-tls \
     --cert=/secure/next/tls.crt --key=/secure/next/tls.key --dry-run=client -o yaml \
     | kubectl apply -f -
   kubectl -n bailiff-webhook rollout restart deployment/bailiff-release-webhook
   kubectl -n bailiff-webhook rollout status deployment/bailiff-release-webhook
   ```

4. Render and apply the registration again with only the new CA certificate, then run the webhook audit.

Schedule this rotation well before 90 days and alert on the deadline; the binary does not renew certificates automatically. Pin the webhook image by digest. Confirm timeouts under TLS load on the target cluster before production use, and verify the two replicas occupy separate nodes before Enforce.
